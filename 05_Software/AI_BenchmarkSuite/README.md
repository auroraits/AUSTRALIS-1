# AUSTRALIS AI Benchmark Suite

**Revision:** 2026-07-31
**Estado:** Active
**Trazabilidad:** `05_Software/AI PAYLOAD/AI_AGENT_PROTOCOL.md`, `05_Software/AI PAYLOAD/MODEL_ASSETS.md`, `08_Decisions/ADR-20260727-ai-payload-gemma4-e2b-candidate.md`

Open benchmark and operations suite for the AUSTRALIS-1 experimental AI
payload.

Version 0.2 uses a distributed lab architecture:

- one central dashboard can run on any PC in the network;
- every benchmarked machine runs a small node agent;
- the dashboard registers node agents by HTTP endpoint;
- telemetry and inference remain associated with the remote node that produced
  them;
- a node can advertise `telemetry+inference` or `telemetry-only`;
- localhost all-in-one operation remains a development convenience, not the
  base topology.

No result generated by this suite declares a model validated for flight or
flight-ready.

## Layout

```text
05_Software/AI_BenchmarkSuite/
  agent/                 Python dashboard host and remote node agent
  console/               Central browser operations console, no build step
  docs/                  Architecture, install, security, export, simulator bridge
  examples/              Sanitized distributed-node and session examples
  scenario-packs/        AUSTRALIS presets and deterministic scoring metadata
  schemas/               JSON Schemas for public artifacts
```

## Recommended Topology

```text
Central operations PC
  dashboard-only Python host
  browser console
        |
        +---- HTTP/SSE ---- PC node agent ---- local Ollama/runtime
        |
        +---- HTTP/SSE ---- CM5 node agent --- local llama.cpp
        |
        +---- HTTP/SSE ---- telemetry-only node agent
```

The browser does not read telemetry from the dashboard PC unless that PC is
separately registered as a node. An `inference_endpoint` is resolved by the
remote agent, so `http://127.0.0.1:8082` means port 8082 on that node.

## Quick Start v0.2

### 1. Start the central dashboard host

From the suite directory:

```powershell
python .\agent\australis_benchmark_agent.py --dashboard-only
```

Open:

```text
http://127.0.0.1:8765/
```

`--dashboard-only` serves the console, scenario pack, and ZIP exporter. It
does not expose node telemetry or accept inference.

### 2. Start a telemetry and inference node

Run on the machine that owns the inference runtime:

```powershell
python .\agent\australis_benchmark_agent.py `
  --host 0.0.0.0 `
  --node-name prestage-node-a `
  --stage pre-staging `
  --node-type pc-windows `
  --runtime ollama `
  --model gemma4:e2b `
  --inference-endpoint http://127.0.0.1:11434
```

### 3. Register the node

In `Nodes`:

1. Select `New node`.
2. Enter a unique name and the node agent endpoint.
3. Enable telemetry and inference capabilities.
4. Enter the runtime endpoint as seen by that node agent.
5. Save and run the per-node health check.

Health discovery records the agent role, version, capabilities, and last
latency. The registry is stored in that browser's local storage.

### 4. Run the minimum regression

Select E05, E09, and E12, then run with `repeats=1`. The global concurrency
limit applies across every enabled inference-capable node.

Enabled telemetry-only nodes remain visible in telemetry but are skipped by
the inference queue with an explicit reason.

## Agent Roles

### Telemetry and inference

Default role. Endpoints include telemetry SSE and inference proxy.

```bash
python agent/australis_benchmark_agent.py \
  --host 0.0.0.0 \
  --node-name node-a \
  --runtime ollama \
  --model gemma4:e2b \
  --inference-endpoint http://127.0.0.1:11434
```

### Telemetry only

```bash
python agent/australis_benchmark_agent.py \
  --host 0.0.0.0 \
  --node-name telemetry-a \
  --telemetry-only
```

The agent advertises inference as unavailable and returns
`capability_disabled` if `/api/infer` is called.

### Dashboard only

```bash
python agent/australis_benchmark_agent.py --dashboard-only
```

This role is a central static/scenario/export host. Do not register it as a
benchmark node unless it is restarted in a node role.

## Operations Console

The console keeps telemetry and run state visible without desktop page scroll:

- compact command bar for fleet health, queue control, abort, and export;
- left configuration drawer for nodes, inference, episodes, snapshot, and
  prompt preview;
- metric-track telemetry chart with per-node colors and unavailable states;
- run lifecycle markers with event hover details;
- per-node queue progress and clickable run rows;
- run detail drawer with prompt, snapshot, raw response, parsed JSON, scoring
  explanations, events, and interval telemetry.

Metric toggles include CPU, memory, available memory, CPU/CM5/GPU temperature,
disk, tokens/s, latency, power, and energy. A series is only drawn when the
remote agent or runtime reports that metric.

## Runtime Support

The node agent proxies:

- Ollama `/api/generate`;
- llama.cpp `/completion`;
- llama.cpp/OpenAI-compatible `/v1/chat/completions`;
- generic OpenAI-compatible chat completions.

The CM5 operational baseline remains llama.cpp. Ollama is acceptable for
pre-staging and model preparation, not as the CM5 staging runtime baseline.

## Scoring and Failure Detail

The deterministic console scorer records:

- strict JSON parse and missing fields;
- expected tools found and missing;
- prohibited tools detected;
- hard-fail supervisor rules with explanations;
- soft warnings with human-readable reasons;
- optional summary and behavior-log quality;
- configured latency and tokens/s warnings;
- remote telemetry coverage during each run.

Latency and throughput warning thresholds are opt-in. Empty thresholds do not
invent a warning limit.

## Run Lifecycle

Every run can record:

```text
queued
inference_start
request_sent
first_byte_or_first_token   when the runtime reports it
response_received
generation_complete
scoring_complete
timeout | error | abort
```

The current non-streaming proxy always records request, response, and scoring
boundaries. It only records first-token timing when a runtime supplies a real
metric.

## Export

The central host downloads a sanitized ZIP:

```text
manifest.json
results.jsonl
results.csv
events.jsonl
telemetry.jsonl
prompts/
raw_responses/
scoring.json
config.sanitized.json
report.md
```

If no ZIP exporter is reachable, the console offers a sanitized session JSON
fallback. Individual runs can also be copied or exported as JSON from the run
detail drawer.

## v0.2 Acceptance Criteria

1. The dashboard starts with no implicit local benchmark node.
2. Node add, edit, duplicate, delete, enable/disable, unique-name validation,
   and per-node health checks work independently.
3. Health metadata distinguishes telemetry, inference, scenario, and export
   capabilities.
4. Selected episodes, repeats, and sweeps queue across all enabled
   inference-capable nodes under one global concurrency limit.
5. Telemetry-only nodes never receive inference requests and have an explicit
   skip reason.
6. Run state exposes queued, running, completed, failed, timeout, and aborted
   outcomes.
7. Telemetry series identify node, metric, unit, and unavailable state without
   synthesizing missing measurements.
8. Lifecycle markers identify run, node, episode, timestamp, and event duration.
9. Run detail includes all input, output, scoring, and interval-telemetry
   evidence.
10. ZIP exports include detailed warnings and run events while preserving
    redaction.
11. Agent self-test, Python compile, JavaScript syntax, JSON parsing, and public
    safety scans pass.

## Design Limits

- Power and energy remain unavailable unless a real source reports them.
- CM5 thermal and throttling data are best-effort via `vcgencmd`.
- NVIDIA GPU telemetry is best-effort via `nvidia-smi`.
- `psutil` is optional. Without it, CPU/memory/process telemetry is reduced.
- The simulator bridge remains a phase-2 adapter stub.
- The development agent has no authentication and permits CORS. Use it on a
  controlled benchmark network and do not put secrets in node config or prompts.
